# Trading Journal

Личный трейд-журнал с риск-менеджментом. Вход по почте и паролю (Better Auth),
у каждого пользователя свой торговый счёт.
Next.js (App Router) + Postgres (Neon) через Prisma, деплой на Vercel.

## Локальный запуск

```bash
npm install
cp .env.example .env   # заполнить DATABASE_URL, ANTHROPIC_API_KEY, BETTER_AUTH_*, OWNER_EMAIL, APP_PASSWORD
npx prisma migrate dev
npm run dev
```

Потом открыть `/setup` и создать учётку владельца (см. «Вход и пользователи»).

### Переменные окружения

| Переменная          | Назначение                                              |
| ------------------- | ------------------------------------------------------- |
| `DATABASE_URL`      | строка подключения к Postgres (Neon)                     |
| `ANTHROPIC_API_KEY` | ключ для разбора скриншотов, только на сервере           |
| `BETTER_AUTH_SECRET` | секрет подписи сессий, свой на каждое окружение          |
| `BETTER_AUTH_URL`   | адрес сайта; на превью не нужен — берутся адреса деплоя  |
| `OWNER_EMAIL`       | почта владельца: роль admin и существующие сделки       |
| `APP_PASSWORD`      | старый общий пароль, нужен один раз для `/setup`         |
| `VISION_MODEL`      | модель для разбора скриншотов, по умолчанию `claude-haiku-4-5` |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | сигналы безопасности в Telegram, необязательно |

## Деплой на Vercel + Neon

1. Импортировать репозиторий в Vercel.
2. Подключить Neon через Vercel-интеграцию — она сама заводит `DATABASE_URL`.
3. Добавить `ANTHROPIC_API_KEY`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `OWNER_EMAIL`
   и `APP_PASSWORD` в Environment Variables.
4. Задеплоить: `npm run build` прогоняет `prisma migrate deploy` перед сборкой.
5. Открыть `/setup` и создать владельца — торговый счёт создастся или
   привяжется сам.

## Структура

```
prisma/schema.prisma          Account / BalanceEvent / Trade / Fix
src/lib/trading-math.ts       формулы: risk, position size, закрытие сделки
src/lib/risk-budget.ts        бюджет риска и его зоны
src/app/api/**                route handlers (zod-валидация, транзакции)
src/app/(pages)               дашборд, /trades/new, /trades/[id], /trades, /settings
```

### Что важно знать про расчёты

- Все денежные вычисления идут на сервере; клиент считает live-превью тем же
  `lib/trading-math.ts` — логика не продублирована.
- `Trade` хранит снапшоты `depositAtEntry` и `feeRateAtEntry`, поэтому изменение
  настроек не меняет уже открытые сделки.
- Сделка закрывается автоматически, когда сумма `sizePct` фиксаций достигает 100:
  в одной транзакции считается результат, создаётся `BalanceEvent` типа
  `trade_settlement` и обновляется баланс аккаунта.
- Баланс нельзя изменить напрямую через `PATCH /api/account` — только через
  `BalanceEvent` или закрытие сделки.
- Параметры открытой сделки можно поправить (`PATCH /api/trades/:id`): riskAmount и
  positionSize пересчитываются, а снапшоты депозита и комиссии остаются прежними.
  У закрытой сделки правка запрещена.
- `realizedRR` — знаковый R-мультипликатор `netPnL / riskAmount`. Это осознанное
  отступление от формулы раздела 4 ТЗ, которая брала модуль хода цены и поэтому
  давала убыточной сделке положительный R:R.
- Скриншоты разбирает модель из `VISION_MODEL` (по умолчанию `claude-haiku-4-5`).
  Без `ANTHROPIC_API_KEY` приложение работает полностью, кроме кнопки загрузки
  скриншота — она вернёт понятную ошибку, а сделка заводится руками.
- Модель сообщает роль уровня (`entry` / `stop` / `target`) и направление только
  когда это уже помечено на графике — цветом плашки на ценовой шкале или зонами
  инструмента позиции. Помеченное подставляется в поля, но остаётся в списке
  кандидатов и правится одним кликом: последнее слово за пользователем.
  Плашку текущей цены модель путает со входом, поэтому промпт явно запрещает
  роль "entry" для текущей цены, а форма дополнительно отбрасывает такой уровень.
  По умолчанию стоит `claude-haiku-4-5` — он примерно в семь раз дешевле и втрое
  быстрее. Цена решения известна и принята владельцем журнала: на замерах по
  реальному насыщенному снимку (индикаторы, сетка, несколько зон) Haiku промахнулся
  по входу в 3 попытках из 3 и путал подписи ценовой сетки с прочерченными
  уровнями, тогда как `claude-opus-5` дал 3/3. Подставленные вход и стоп всегда
  видны в списке кандидатов и правятся в один клик — на это здесь и расчёт.
- Разбор принимает и загруженный файл, и ссылку на снимок TradingView
  (`tradingview.com/x/…`): страница снимка отдаёт прямую ссылку на PNG в og:image.
  Ссылку на живой график (`/chart/…`) так забрать нельзя — там JS-приложение, а
  og:image у него стоковый; для неё из адреса читаются только тикер и таймфрейм.
- `max_tokens` для разбора — 4096: у моделей с рассуждением его токены тоже
  входят в лимит, и на насыщенном графике ответ занимает под 2000. При обрезке
  эндпоинт отвечает ошибкой, а не пустым результатом.
- Плечо (`Trade.leverage`, по умолчанию из `Account.defaultLeverage`, 5×) на риск
  не влияет: убыток при стопе считается от номинала позиции. Плечо определяет
  только маржу — `positionSize / leverage`, ту часть депозита, что реально уходит
  в сделку. На дашборде под бюджетом риска отдельная шкала «Маржа в сделках»,
  в форме — предупреждение, если маржа больше баланса.
- Лимит бюджета риска — поле `Account.riskLimitPct` (потолок суммарного риска
  открытых позиций в процентах от баланса, по умолчанию 3%), редактируется в
  `/settings`. Жёлтая зона начинается после 2/3 лимита.

### Несколько входов (добор)

У сделки может быть несколько входов (`TradeEntry`), как у позиции на бирже в
одностороннем режиме: одна позиция, средний вход, один стоп. `entryPrice`,
`positionSize` и `riskAmount` сделки — производные от входов и стопа
(`src/lib/entries-math.ts`, покрыто тестами):

- средний вход — по количеству монет: 0,1 BTC по 60 000 и 0,1 по 61 000 → 60 500;
- риск — со знаком по входам, то есть количество × (средний вход − стоп): стоп
  на уровне первого входа после добора законен, эта часть на стопе в нуле;
- стоп проверяется относительно среднего входа, а не каждого;
- проценты риска — от депозита на момент первого входа;
- фиксации и итог считаются от среднего входа и не зависят от того, сколько
  было входов — прибыль от цены линейна.

Добор — на странице открытой сделки, пока нет фиксаций; последний добор
можно снять. Две открытые сделки по одной паре и в одну сторону (без
фиксаций) можно объединить: более поздняя становится добором к более ранней,
стоп берётся у поздней, теги объединяются, заметки склеиваются. Объединение
необратимо и не оптимистично — ждёт ответа сервера.

У сделки с несколькими входами правка параметров переносит стоп с
сохранением количества монет (риск пересчитывается); цену входа, риск и
направление там не правят.

### Состояние на клиенте и оптимистичные обновления

Страница сделки после первого SSR живёт в кеше TanStack Query (ключ
`['trade', id]`, `src/lib/query/`). Фиксации добавляются и удаляются
оптимистично: `onMutate` патчит кеш и делает снимок, `onError` откатывает,
`onSuccess` кладёт серверный ответ, `onSettled` сверяется. Локальный расчёт —
`src/lib/trade-local.ts` на той же `lib/trading-math`, поэтому после
подтверждения цифры не меняются. Новая сделка открывается как карточка на
месте формы: DTO считается локально, URL подменяется через `replaceState`,
POST уходит в фоне. Id сделок и фиксаций генерирует клиент (uuid), сервер
идемпотентен по ним. Запросы, зависящие от ещё не сохранённой сделки, ждут её
через `src/lib/query/pending.ts`. Ошибки не молчат: полоска с причиной,
«Повторить» и «Скрыть». Devtools Query открываются кнопкой слева внизу.

Блок «Разбор» (теги причин входа и заметка) правится и у закрытых сделок.
Теги сделки лежат в кеше рядом со сделкой (`{ trade, fixes, tagIds }`), а не
внутри: ответы на правку сделки тегов не содержат и иначе затирали бы их.
Тег включается оптимистично, а запросы одной сделки уходят строго по очереди
(`src/lib/query/serial.ts`), чтобы быстрые тапы дошли до сервера в том же
порядке. Встроенный `scope` у мутаций не подошёл: он продолжает очередь только
на видимой странице. Заметка сохраняется сама — через паузу в наборе и при
уходе с поля.

Под заметкой — «Похоже на: + cme»: теги, упомянутые в тексте, но не отмеченные
(`src/lib/tag-suggest.ts`, без ИИ). Короткие теги (до 3 символов) ищутся только
целым словом, длинные — по основе, чтобы не мешали окончания: «дивергенция»
находится в «дивергенции». Правила покрыты тестами: `npm test` (встроенный
`node:test`, TypeScript через `tsx`).

### Вход и пользователи

- Пользователи, сессии и хеши паролей — [Better Auth](https://better-auth.com),
  таблицы `user`, `session`, `authAccount` в той же базе. Торговый `Account`
  привязан к пользователю через `userId`, `getAccount()` берёт счёт по сессии.
- `src/proxy.ts` (в Next 16 так называется middleware) проверяет сессию на
  каждом запросе целиком, а не только наличие cookie: сессия ищется в базе.
  Кеш сессии в cookie выключен, поэтому выход на других устройствах и смена
  пароля действуют сразу.
- Сессия живёт 30 дней с последнего захода.
- Вход по паролю — только через `/api/login`, эндпоинт Better Auth
  `/sign-in/email` закрыт (`disabledPaths`), чтобы защиту ниже нельзя было обойти.
- Регистрации нет. Первый пользователь создаётся на одноразовой странице
  `/setup`: почта из `OWNER_EMAIL`, новый пароль и старый `APP_PASSWORD` как
  подтверждение. Владелец получает роль admin, доступ к разбору скриншотов и
  существующий торговый счёт. После этого `/setup` отдаёт 404.
- Остальные — по приглашению: админ в «Настройки → Пользователи» вводит почту
  и получает ссылку `/invite/<токен>`, пересылает её сам (писем приложение не
  шлёт). Ссылка одноразовая, живёт 7 дней, её можно отозвать; новое
  приглашение на ту же почту отзывает прежнее. В `Invite` хранится только
  SHA-256 токена. По ссылке заводится учётка ровно на эту почту, с ролью user
  и своим пустым торговым счётом.
- Разбор скриншотов стоит денег, поэтому он по флагу `canParseScreenshots`:
  админ включает его переключателем в «Пользователях», у владельца он включён с
  `/setup`. Без флага `/api/parse-screenshot` отвечает 403, а на форме сделки
  нет ни блока скриншота, ни разбора снимка по ссылке.
- Забытый пароль сбрасывается ссылкой `/reset/<токен>`, которую выписывает
  админ: одноразовая, 24 часа, хранится только хеш. По ней задаётся новый
  пароль, все прежние сессии пользователя удаляются. Админам ссылку не выписать —
  иначе один админ мог бы войти в учётку другого; свой пароль админ меняет в
  настройках.

### Защита входа

- Каждая попытка входа пишется в `LoginAttempt` **до** проверки пароля — так
  пачка параллельных запросов не проскакивает проверку лимита.
- С одного IP — не больше 5 неудачных попыток за 15 минут, дальше `429` с
  `Retry-After`. Во время блокировки даже верный пароль получает отказ, а новые
  попытки продлевают блокировку. Неверный пароль отвечает с задержкой 0,5 с.
- Пароль проверяет Better Auth (scrypt). `APP_PASSWORD` на `/setup` сравнивается
  за постоянное время (`timingSafeEqual` по SHA-256).
- Сигналы в Telegram: блокировка IP, массовый перебор (30 неудачных за час с
  разных адресов — вход при этом не закрывается), вход с нового IP или из новой
  страны. Отправляются после ответа через `after()`, вход не тормозят.
- Дедупликация сигналов атомарна: ключ с номером окна времени вставляется в
  `SecurityAlert` с уникальным индексом через `ON CONFLICT DO NOTHING`, сигнал
  отправляет только тот запрос, чья вставка прошла.
- IP, страну и город ставит Vercel в заголовки `x-real-ip` и
  `x-vercel-ip-country`/`-city` — клиент их подделать не может. Журналы старше
  90 дней чистятся при успешном входе.

## Перенос истории из Google-таблицы

Разовая миграция старого журнала. Таблица должна быть открыта по ссылке —
экспорт CSV идёт без авторизации.

```bash
npx tsx scripts/import-sheet.ts <ссылка-на-таблицу>           # показать, что будет
npx tsx scripts/import-sheet.ts <ссылка-на-таблицу> --apply   # записать в БД
```

Результаты пересчитываются формулами приложения, а не берутся из колонок
таблицы, поэтому расходятся с ней в пределах копейки на округлении. Повторный
запуск безопасен: сделка с теми же входом, стопом и направлением пропускается.
Незакрытые сделки (сумма фиксаций не равна 100%) не переносятся.
